# SyncClass — ERP Import Mapping

**Document:** `docs/ERP_IMPORT.md`
**Audience:** whoever performs the ERP export (registrar, MIS, department secretary)
**Purpose:** a checklist of exactly which SyncClass tables are fed from the ERP,
which columns each one needs, which keys must be unique, and the order to load
them in.
**Related:** `docs/DATABASE.md` (data dictionary), `database/schema/syncclass_complete.sql` (physical schema)

---

## 1. What is copied and what is not

SyncClass has 30 tables. Only **reference data** comes from the ERP. Everything
SyncClass produces itself — schedules, conflicts, comments, tasks, change
requests, notifications, the activity log, login attempts, remember tokens, the
RBAC matrix (`roles`, `permissions`, `role_permissions`), `settings` and
`schema_migrations` — is **never imported**. Importing any of it would overwrite
the permission catalogue and invalidate stored conflict state.

| Group | Tables | Source |
|---|---|---|
| Reference data (import) | `departments`, `users`, `faculty_profiles`, `buildings`, `rooms`, `academic_years`, `semesters`, `time_slots`, `subjects`, `sections`, `section_subjects`, `faculty_subjects`, `faculty_availability` | ERP / SIS |
| Operational data (never import) | `schedules`, `schedule_conflicts`, `schedule_comments`, `comment_mentions`, `change_requests`, `tasks`, `task_assignments`, `task_checklist_items`, `notifications`, `activity_log` | SyncClass only |
| Security / configuration (never import) | `roles`, `permissions`, `role_permissions`, `users.password_hash` (reset instead), `remember_tokens`, `login_attempts`, `settings`, `schema_migrations` | SyncClass only |

**Deployment sequencing:** import *after* `database/schema/syncclass_complete.sql`
has been loaded (it creates the tables, the roles and the demo accounts), and
*before* the first semester is scheduled. Importing into an empty schema without
the roles seed leaves `users.role_id` with nothing to point at.

## 2. Import order (foreign-key safe)

Load in exactly this sequence. A later step needs the surrogate IDs created by
an earlier one.

| # | Target table | Depends on | ERP source (typical) |
|---|---|---|---|
| 1 | `departments` | — | Department / college master |
| 2 | `users` | `departments` | Employee / user account master |
| 3 | `departments` (post-pass: `dean_user_id`) | `users` | Department head assignment |
| 4 | `faculty_profiles` | `users`, `departments` | Teacher / employee record |
| 5 | `buildings` | — | Facility / building master |
| 6 | `rooms` | `buildings` | Room master |
| 7 | `academic_years` | — | School year calendar |
| 8 | `semesters` | `academic_years` | Term / grading period calendar |
| 9 | `time_slots` | — | Bell schedule / period master |
| 10 | `subjects` | `departments` | Course / subject catalog |
| 11 | `sections` | `departments` | Section / block / program-year group |
| 12 | `section_subjects` | `sections`, `subjects`, `semesters` | Curriculum, or class/subject offerings |
| 13 | `faculty_subjects` | `faculty_profiles`, `subjects` | Qualification matrix (often missing in ERP) |
| 14 | `faculty_availability` | `faculty_profiles` | Load / availability windows (often missing in ERP) |

Steps 1 → 2 → 3 exist because `departments.dean_user_id` and `users.department_id`
reference each other. Load users with `department_id`, then set the deans with an
`UPDATE` in step 3 rather than trying to insert both directions at once.

## 3. Per-table checklist

For each table: the columns to export (**bold** = required, *italic* = required
but auto-generated by SyncClass), the unique keys the export must satisfy, and
the validation to apply in the export file before loading.

### 3.1 `departments` — 1 department per college

| Column | Type | Rule |
|---|---|---|
| **`code`** | VARCHAR(20) | **UNIQUE**, upper-case, no spaces |
| **`name`** | VARCHAR(150) | full name, e.g. "College of Computer Studies" |
| `short_name` | VARCHAR(50) | short label used in chips and reports |
| `dean_user_id` | INT UNSIGNED | NULL on first load — see step 3 above |
| `email` | VARCHAR(150) | department mailbox |
| `phone` | VARCHAR(30) | |
| `color_hex` | CHAR(7) | default `#8C1D40`; keep the seeded colours (BUS `#008000`, CSM `#808000`, EDU `#000080`, ENGR `#400040`, HSS `#AF640F`) so existing schedules keep their colour |
| `is_active` | TINYINT(1) | `1` unless the department is dissolved |

Ensure the five seeded departments are matched by `code` and updated, not
inserted a second time under a different code.

### 3.2 `users` — deans, secretaries, faculty, administrators

| Column | Type | Rule |
|---|---|---|
| **`role_id`** | INT UNSIGNED | map the ERP role to a SyncClass `roles.code` (`admin`, `dean`, `secretary`, `faculty`); never copy the ERP role id |
| `department_id` | INT UNSIGNED | NULL for `admin` |
| **`email`** | VARCHAR(150) | **UNIQUE**; must be the login address, normally `name@sac.edu.ph` |
| **`username`** | VARCHAR(60) | **UNIQUE**; derive from the email local part |
| **`password_hash`** | VARCHAR(255) | see §5 — do not copy ERP hashes |
| **`first_name`**, **`last_name`** | VARCHAR(80) | |
| `middle_name` | VARCHAR(80) | |
| `employee_no` | VARCHAR(30) | **UNIQUE** when present; NULL if the ERP has none |
| `phone` | VARCHAR(30) | |
| `is_active` | TINYINT(1) | `0` for resigned/retired staff — never hard-delete |

Export only staff who need to sign in. Students are not SyncClass users.

### 3.3 `faculty_profiles` — 1 row per teacher

| Column | Type | Rule |
|---|---|---|
| **`user_id`** | INT UNSIGNED | **UNIQUE**, 1:1 with `users`; `ON DELETE CASCADE` |
| **`department_id`** | INT UNSIGNED | home department (a teacher may still teach another department's section; the scheduler allows it) |
| `employment_type` | ENUM | `full_time` \| `part_time` \| `visiting` |
| `max_load_units` | DECIMAL(4,1) | default `18.0`, must be `> 0`; this is the workload cap used by the generator |
| `specialization` | VARCHAR(180) | free text |
| `office` | VARCHAR(80) | room/building of the office, not a schedulable room |
| `is_active` | TINYINT(1) | |

### 3.4 `buildings`

| Column | Type | Rule |
|---|---|---|
| **`code`** | VARCHAR(20) | **UNIQUE** (seeded: `MAIN`, `SCI`, `ENGH`, `HSC`) |
| **`name`** | VARCHAR(120) | |
| `campus` | VARCHAR(120) | |
| `address` | VARCHAR(255) | |
| `is_active` | TINYINT(1) | `0` for buildings being demolished/closed, keeping their history |

### 3.5 `rooms` — the schedulable resource

| Column | Type | Rule |
|---|---|---|
| **`building_id`** | INT UNSIGNED | must exist in `buildings` |
| **`code`** | VARCHAR(20) | unique **per building**, e.g. `R101` inside `ENGH` |
| `name` | VARCHAR(120) | |
| `floor` | SMALLINT | ground floor = `1`, basement `0` |
| `room_type` | ENUM | `lecture` \| `laboratory` \| `seminar`; drives room matching, so map lab rooms to `laboratory` |
| **`capacity`** | SMALLINT UNSIGNED | `> 0`; compared against `sections.student_count` |
| `facilities` | VARCHAR(500) | comma-separated free text (projector, AC, …) |
| `is_active` | TINYINT(1) | `0` for rooms withdrawn from scheduling; **exclude** them from the timetable but keep the row |

### 3.6 `academic_years`

| Column | Type | Rule |
|---|---|---|
| **`code`** | VARCHAR(20) | **UNIQUE**, e.g. `2026-2027` |
| **`start_date`**, **`end_date`** | DATE | `end_date > start_date` (CHECK) |
| `is_current` | TINYINT(1) | exactly one `1` across the table |

### 3.7 `semesters` — the terms

| Column | Type | Rule |
|---|---|---|
| **`academic_year_id`** | INT UNSIGNED | |
| **`term_no`** | TINYINT | `1`–`3`; unique together with the academic year |
| **`name`** | VARCHAR(40) | e.g. "First Semester" |
| **`code`** | VARCHAR(30) | **UNIQUE**, e.g. `2026-2027-1` |
| **`start_date`**, **`end_date`** | DATE | `end_date > start_date` |
| `status` | ENUM | `planned` \| `active` \| `closed`; schedules can only be written into `planned`/`active` terms |
| `is_current` | TINYINT(1) | exactly one `1`; `TermRepository` clears the previous one |

### 3.8 `time_slots` — the bell schedule

| Column | Type | Rule |
|---|---|---|
| **`code`** | VARCHAR(20) | **UNIQUE**, e.g. `T0700` |
| **`label`** | VARCHAR(50) | e.g. "07:00 – 08:30" |
| **`start_time`**, **`end_time`** | TIME | `end_time > start_time` |
| `is_break` | TINYINT(1) | `1` for institutional break periods (reference only — the enforced windows come from `config/schedule.php`) |
| `sort_order` | TINYINT UNSIGNED | display order |
| `is_active` | TINYINT(1) | |

Optional. Schedules store free `start_time`/`end_time` values, not slot ids, and
no scheduling code reads this table today — the enforced break windows come from
`config/schedule.php` (`schedule.breaks`). Import it only to keep the reference
list aligned with the ERP; skipping it changes no scheduling behaviour.

### 3.9 `subjects` — the catalog

| Column | Type | Rule |
|---|---|---|
| **`code`** | VARCHAR(30) | **UNIQUE**, e.g. `bus104` / `BUS104` — pick one casing for the whole file |
| **`title`** | VARCHAR(180) | |
| **`department_id`** | INT UNSIGNED | owning department; the "subject must match the section's department" rule is evaluated against this column |
| `units` | DECIMAL(4,1) | `>= 0` |
| `lecture_hours` | DECIMAL(4,1) | `>= 0` |
| `lab_hours` | DECIMAL(4,1) | `>= 0` |
| *`contact_hours`* | DECIMAL(4,1) | **do not export** — generated column (`lecture_hours + lab_hours`) |
| `subject_type` | ENUM | `lecture` \| `laboratory` \| `mixed` |
| `preferred_room_type` | ENUM | `lecture` \| `laboratory` \| `seminar` \| NULL |
| `description` | TEXT | |
| `is_active` | TINYINT(1) | `0` for retired subjects |

### 3.10 `sections` — the class groups

| Column | Type | Rule |
|---|---|---|
| **`code`** | VARCHAR(30) | **UNIQUE**, e.g. `BA-1A` |
| `name` | VARCHAR(120) | display name |
| `program` | VARCHAR(120) | e.g. "BS Business Administration" |
| `year_level` | TINYINT | `1`–`6` |
| **`department_id`** | INT UNSIGNED | |
| **`student_count`** | SMALLINT UNSIGNED | `> 0`; **use the real enrolment figure** — it is what capacity matching and room suggestions use |
| `is_active` | TINYINT(1) | `0` for sections that no longer exist; export only the terms being scheduled |

Export the section per **term** when the ERP reuses a code across terms — a
section code must be unique in SyncClass, so either suffix it with the term
(`BA-1A-2026-1`) or keep one live row per code.

### 3.11 `section_subjects` — the curriculum / demand input

| Column | Type | Rule |
|---|---|---|
| **`section_id`** | INT UNSIGNED | |
| **`subject_id`** | INT UNSIGNED | |
| `semester_id` | INT UNSIGNED | NULL = applies to any term for that section |
| `required_meetings` | TINYINT | `1`–`6` weekly meetings; default `1` |
| `is_active` | TINYINT(1) | |

Unique key is `(section_id, subject_id, semester_id)`. **Note:** because
`semester_id` is nullable, MySQL permits duplicate `(section, subject, NULL)`
rows — the export must de-duplicate those itself.

This table is what the generator schedules. If the ERP has a *class offering /
subject offering* table (section + subject + term + teacher), export that; a
curriculum table plus the term is the fallback.

### 3.12 `faculty_subjects` — who can teach what

| Column | Type | Rule |
|---|---|---|
| **`faculty_id`** | INT UNSIGNED | |
| **`subject_id`** | INT UNSIGNED | |
| `proficiency` | ENUM | `primary` \| `secondary` |

Unique on `(faculty_id, subject_id)`. Usually maintained in SyncClass rather
than exported; if the ERP has no qualification data, skip this table and build
it once through the Faculty screen.

### 3.13 `faculty_availability` — when a teacher can teach

| Column | Type | Rule |
|---|---|---|
| **`faculty_id`** | INT UNSIGNED | |
| **`day_of_week`** | TINYINT | `1` = Monday … `7` = Sunday |
| **`start_time`**, **`end_time`** | TIME | `end_time > start_time` |
| `availability_type` | ENUM | `available` \| `preferred` \| `unavailable` |
| `note` | VARCHAR(255) | reason, shown in the scheduler |

Intervals are half-open (`[start, end)`), so adjacent windows do not overlap.
`unavailable` is used to carve a gap inside a wider `available` range (lunch,
department meeting). Rarely present in an ERP — build it in SyncClass if absent.

## 4. Export file conventions

One CSV per table, named after the target table: `departments.csv`,
`subjects.csv`, … Each file has:

- a single header row using the SyncClass column names from §3, in any order;
- UTF-8 **without BOM**;
- ISO dates `YYYY-MM-DD`, times `HH:MM:SS` (24-hour), booleans `0`/`1`;
- quotes around any field containing a comma, quote or newline; escape an
  embedded quote by doubling it;
- no `id` column — SyncClass assigns its own surrogate keys. Cross-table
  references are exported as the **natural code**, not the ERP id (see §6);
- no trailing blank rows; empty file content must be `header only`.

## 5. Credentials for imported users

Do **not** copy ERP password hashes — SyncClass verifies with
`password_hash()`/`password_verify()` and the ERP hash format will not match.

Choose one: either set `must_change_password = 1` with a temporary password
issued out-of-band, or import the accounts with login disabled and send
activation links. Never write a shared default password into the CSV.

Administrators are expected to re-review the `roles`/`role_permissions` matrix
after import; it is seeded by the schema and must not be modified by the export.

## 6. Keys, codes and repeat imports

SyncClass has no ERP-id column. Two workable strategies:

1. **One-time load** (recommended for a first migration): normalise codes in the
   ERP export, load once in §2 order, and let SyncClass own the data afterwards.
2. **Repeatable sync**: keep a separate mapping table (`erp_map(source_table,
   source_id, syncclass_id)`) or prefix every code with the ERP key, and upsert
   by natural code. A plain re-import without a mapping will create duplicates,
   because each Natural key is `UNIQUE` on its code — a duplicate code aborts
   the load rather than silently merging.

Rules for codes either way:

- Trim whitespace, collapse internal double spaces, normalise case (upper-case
  department/building/room/subject/section codes).
- Never change a code that already has schedules attached; archive it instead.
- Keep the seeded codes for `departments`, `buildings` and the demo accounts
  where they describe the same real entity.

## 7. Pre-load verification queries

Run these against the export (in the staging schema) before touching SyncClass.
Every query must return **0 rows**.

```sql
-- duplicate natural keys
SELECT code, COUNT(*) FROM departments GROUP BY code HAVING COUNT(*) > 1;
SELECT code, COUNT(*) FROM subjects    GROUP BY code HAVING COUNT(*) > 1;
SELECT code, COUNT(*) FROM sections    GROUP BY code HAVING COUNT(*) > 1;
SELECT code, COUNT(*) FROM buildings   GROUP BY code HAVING COUNT(*) > 1;
SELECT code, COUNT(*) FROM academic_years GROUP BY code HAVING COUNT(*) > 1;
SELECT code, COUNT(*) FROM semesters   GROUP BY code HAVING COUNT(*) > 1;
SELECT email, COUNT(*) FROM users GROUP BY email HAVING COUNT(*) > 1;
SELECT employee_no, COUNT(*) FROM users
 WHERE employee_no IS NOT NULL GROUP BY employee_no HAVING COUNT(*) > 1;

-- orphan references
SELECT r.* FROM rooms r LEFT JOIN buildings b ON b.id = r.building_id
 WHERE b.id IS NULL;
SELECT s.* FROM sections s LEFT JOIN departments d ON d.id = s.department_id
 WHERE d.id IS NULL;
SELECT sj.* FROM subjects sj LEFT JOIN departments d ON d.id = sj.department_id
 WHERE d.id IS NULL;

-- invalid values
SELECT * FROM rooms    WHERE capacity <= 0;
SELECT * FROM sections WHERE student_count <= 0 OR year_level NOT BETWEEN 1 AND 6;
SELECT * FROM academic_years WHERE end_date <= start_date;
SELECT * FROM semesters WHERE end_date <= start_date OR term_no NOT BETWEEN 1 AND 3;
SELECT * FROM section_subjects WHERE required_meetings NOT BETWEEN 1 AND 6;
```

## 8. Post-load verification

```sql
-- row counts against the export manifest
SELECT 'departments' t, COUNT(*) n FROM departments
UNION ALL SELECT 'users', COUNT(*) FROM users
UNION ALL SELECT 'faculty_profiles', COUNT(*) FROM faculty_profiles
UNION ALL SELECT 'buildings', COUNT(*) FROM buildings
UNION ALL SELECT 'rooms', COUNT(*) FROM rooms
UNION ALL SELECT 'academic_years', COUNT(*) FROM academic_years
UNION ALL SELECT 'semesters', COUNT(*) FROM semesters
UNION ALL SELECT 'subjects', COUNT(*) FROM subjects
UNION ALL SELECT 'sections', COUNT(*) FROM sections
UNION ALL SELECT 'section_subjects', COUNT(*) FROM section_subjects;

-- every teacher account has a profile, and every profile has a user
SELECT u.id FROM users u JOIN roles r ON r.id = u.role_id
 LEFT JOIN faculty_profiles f ON f.user_id = u.id
 WHERE r.code = 'faculty' AND f.id IS NULL;

-- exactly one current year and one current term
SELECT COUNT(*) FROM academic_years WHERE is_current = 1;  -- expect 1
SELECT COUNT(*) FROM semesters      WHERE is_current = 1;  -- expect 1
```

Then open `/schedules/create` as a secretary and confirm each picker (section,
subject, teacher, room) is populated, and load `/analytics` to confirm the
vacancy grid shows the imported rooms.
